## Competitive conclusion

`INFERENCE` The most defensible remaining wedge is not "another court," "another reputation score," "another proof rail," or "another marketplace." It is a narrow semantic acceptance adapter that sits between agent work and an existing payment/commerce system, uses deterministic proof where possible, and escalates only genuinely subjective residual criteria to GenLayer consensus. SealRail, Recourse, MandateVault, and Nomos mean hashes, commitments, policy gates, and adjudication/payment primitives are already represented; differentiation must come from the typed deliverable policy, adapter-neutral receipt, and operational integration UX.

## Internet Court benchmark

Internet Court is the required primary benchmark. The observations below come from S9/S25 (initial deep inspection, accessed 2026-09-11) and S56 (current MCP tree recheck at commit `11391ba04599a4fbded730e1c6738f9c44cd89fd`, accessed 2026-09-12). Statements about a target architecture or roadmap are not treated as proof that every path is deployed or production-ready.

| Dimension | Inspected finding | Consequence for Proofline |
|---|---|---|
| Product thesis | A general judicial layer for agent agreements: parties define a statement, guidelines, and evidence definitions; mutual agreement resolves directly, while disagreement invokes an AI jury. | Do not pitch a general court. Own routine post-delivery acceptance as the primary event, with later dispute/court integration. |
| Architecture | Documented dual-chain design: Base escrow and agreement state, GenLayer adjudication, LayerZero messaging, REST/SDK interface, and Next.js monitoring surface. The repository tree contains Solidity escrow/bridge code, GenLayer contracts, relay service, frontend, and tests. | Keep the MVP single-network and non-custodial. A finalized acceptance receipt proves the wedge without inheriting bridge and escrow operations. |
| Contract design | `InternetCourt.py` stores two parties, statement, guidelines, evidence definitions, lifecycle state, evidence, proposed outcomes, verdict, and reasoning. Matching party outcomes resolve immediately; disagreement or an explicit call opens a dispute; `prompt_non_comparative` makes only the verdict material for equivalence. | Reuse the discipline, not the identity: versioned acceptance criteria, deterministic evidence validation, bounded result schema, replay guards, and finality-aware reads. |
| Evidence model | Party-specific free-form evidence is constrained mainly by JSON definitions and character limits. The prompt tells validators to ignore unverifiable citations, authority claims, statistics, and embedded instructions. | Differentiate with a canonical evidence manifest, hashes, typed artifacts, deterministic checks, source status, and explicit missing/stale/contradictory reason codes before LLM evaluation. |
| Dispute flow | States progress through created, active, disputed, resolving, and resolved/cancelled. Both parties can submit once; both submissions or an expired evidence window permit resolution; results are party A, party B, or undetermined. Project materials also describe protocol-level appeals. | Make acceptance the normal path rather than dormant litigation. Preserve `UNDETERMINED`; defer custom appeals and bilateral court UX. |
| API | README/PROJECT show intended REST calls for create, resolve/dispute, evidence submission, and verdict queries. In the inspected tree snapshot, no standalone top-level API implementation was visible, so deployed API completeness is `UNVERIFIED`. | Build one small idempotent agent-facing contract/client interface only after approval; do not claim a production API until exercised. |
| Agent integration | The product is explicitly API-first and treats agents as primary users, with wallet-signed operations and a human monitor role. | Keep stable job IDs, evidence payloads, machine-readable statuses, finalized acceptance receipts, and downstream adapter signals primary; UI is an inspector. |
| MCP integration | The current repository tree contains a real top-level `mcp/` implementation (`mcp/src/index.ts`, `mcp/src/tools.ts`) at the S56 commit. | Roadmap | Documented later work includes SDKs, reputation, partial verdicts, richer evidence, templates, pipeline disputes, MCP, more assets, and privacy. | Most obvious extensions are already claimed territory. | Strongest differentiator | Internet Court combines bilateral agreement, mutual resolution, AI-jury recourse, escrow, API positioning, and cross-chain settlement in one coherent story. | Proofline must be demonstrably smaller and faster to integrate, while proving better acceptance evidence semantics. |

`RECOMMENDATION` The decisive non-reproduction boundary is: Internet Court begins with a bilateral court contract and activates a jury on disagreement; Proofline should begin with a machine-readable acceptance policy and produce a finalized acceptance receipt for every submitted deliverable, invoking GenLayer only for the residual subjective criteria. Any payment or escrow consequence remains an external adapter action, not a Proofline claim.
